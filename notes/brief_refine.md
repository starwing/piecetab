# brief_refine.md — 精炼要诀（含铁律细则）

> 记录代码精炼（refine）的核心经验，并收录自 AGENTS.md 迁入的铁律细则（现场状态 / 设计落地 / 修复与正确性）。
> 核心书写铁律见 `notes/brief_writing.md`，会话铁律见 `AGENTS.md`；本文件所有精炼都要在**不违反铁律**的前提下进行。
> 条款编号为“节.条”（如 `2.3`）；新增条款追加新号，既有编号不重排，跨文件引用直接写编号。

## 核心信条

- **精炼不是为了减行数，而是为了减杂质。** 25 行限制是工具，不是目标；为凑行数引入 flag、拆函数、制造短路逻辑都是庸工。改完若不如改前清晰，就是倒退。
- **精髓一句话：计算自然的值，让值引导决策。不要预设答案（flag），然后去核对。**
- **refine 只写【非业务的经验】，不写业务知识**——具体库 / 模块的内部实现细节（函数名、数据结构、特定算法路径）属于业务知识，一律不写入本文件；任务留档也不写。

四种浪费（自查信号）：

| 浪费 | 典型表现 |
|------|----------|
| 预制 flag | 先设 flag，后面再检查 |
| 特例分支 | 为边界情况单开提前 return |
| 多余变量 | 声明了函数后半节不出现 |
| 大块分支 | `if { r=...; if (r != OK) return r; }` 可收成单行 |

**代管是坏味道：本函数写错却靠其他函数兜底，视同未修复；局部错误应局部暴露，而不是由调用方 / 其他 helper 保护。**

## 铁律细则（自 AGENTS.md 迁入）

> AGENTS.md 只保留底线速查；现场状态、设计落地与修复的完整条款以本节为准，重构 / 精炼时逐条对照。

### 现场状态纪律（Cursor / 路径）

- **编辑算法必须自己维护现场状态**：删除 / 插入 / 重排 / 合并等 mutation 返回前，Cursor 的路径与偏移必须是最终正确状态。严禁在 mutation 之后调用定位原语来“修正” Cursor；这视为掩盖错误，同时破坏同族实现的一致性。发现此类修复必须立即停止并报告，改为在算法内部按同族实现正确维护。
- **任何持有 Cursor / 路径等内部现场状态的 helper（非公共 API）都严禁丢弃现场后强制定位**；若确有必要，必须停下来问用户。强制定位意味着信息丢失，【绝对不能接受】。
  - 强制定位包括 locate / advance / lochead / locend 等重新建立位置的操作；内部 helper 必须利用已有 `paths/off/poff` 等现场。
  - 此条针对 **stb-style 单头文件库内部实现**：库内部函数拥有现场信息，禁止丢弃后重新定位。
  - 外部使用方 / 绑定层适配器不属于此约束：它们没有内部现场，使用公开导航原语是正确的。

### 设计落地与算法退化（最高优先级）

- **严禁删除、绕过或替换任何已由 `notes/design_*.md` 落地的算法要求**。实现与 design 冲突时，唯一正确动作是立即停止并报告冲突，不得以“当前模型不适用”“更简单”“更清晰”为理由删改设计。
- 任何重构若改变已定案的算法路径、数据结构或复杂度承诺（如批量算法退化为逐项、共享结构改为复制、结构操作改为内容扫描），必须在改动前明确列为“设计变更”并交用户决策；未获许可不得开工，更不得在提交 / 交接中沉默。
- 每个 agent / subagent 开始任务前必须核对相关 design 章节；交付时必须报告“是否触碰 design 落地的算法要求”。发现他人改动造成算法退化时，必须立即停止当前工作并上报，禁止继续在其上重构或清理。
- subagent 任务若涉及删除 / 替换已落地算法，提示词必须明确禁止，并要求在交付中给出 design 对照结论与全部闸门输出；违反此条视为任务失败。
- **正确性第一，一致性第二**：同类库 / 同类实现默认保持函数形态、块顺序、数据结构、命名和语义一致；一致性服务于可维护性，但绝不能为一致性牺牲正确性。审核顺序是正确性 → 一致性 → 简洁性。
- **允许打破一致性，但必须显式说明**：不一致条目要在交付 / 审核中逐条列出，写清“为什么领域上必要、为什么不能对齐、正确性依据”；获批准后才可保留。禁止悄无声息偏离，禁止用“更简单”“行数更少”“当前模型用不到”当理由。
- **同族实现必须最小差异**：与参考实现相比，除参考库已证实可删的领域代码外，函数形态、块顺序、依赖和语义必须同构。多出来的差异一律先视为实现偏差；不得把实现偏差写进 `design_*.md` 充当“领域差异”保留，只能修实现或停下报告并取得用户明确批准。
- 本规则优先于简洁性、行数、覆盖率、重构计划和历史清理目标。

### 文档计划验证纪律（研究型任务）

- **实现是文档计划的验证手段，不是目的。** 以“照文档计划写实现、确认计划是否可行”为目标的任务，正确性判据是**实现是否逐条落实计划**，而不是测试是否通过；测试全绿不能证明计划可行，也不能证明实现对。
- **遇到阻塞 = 计划有缺陷，动作是修文档。** 实现不下去时，唯一正确顺序是：停下 → 把阻塞归结为计划（design / closure）的哪一条 → 报告用户 → 按裁决修文档 → 再实现。严禁为让测试通过而 case-by-case 改实现——逐例打补丁会把任务拖进死角，并使“计划可行”的结论失去证据效力。
- **阻塞不可解必须立即通知用户**，不得自行连续试多个方案后才上报；出现多个 WIP 迭代本身就是“该上报而未上报”的信号。
- **测试是派生证据，不能反向驱动计划。** 计划与测试冲突时以计划为准，测试按计划重写；禁止改实现去迁就既有测试。
- **同一计划的多份文档必须自洽。** 发现 design 与 closure / plan 对同一条算法要求表述冲突时，先停下报告冲突并请用户裁决以哪份为准，不得自行挑一份照做。

### 修复与正确性

- **禁手术刀式修复**；必寻根因而从源头修，纵改多处调用方亦在所不惜。workaround 视同未修复；禁 orig+restore 模式。
- **局部错误必须局部暴露**；禁止靠其他函数 / 调用方代管兜底来掩盖本函数写错——单头文件库内写错就应直接错。
- **数据应在操作后自然正确，勿依赖事后修正**；helper 提取于正确层级。
- **案例（anchortree stage1，2026-10）：一个同步 bug 被两次掩盖后变成了架构**。链条可复现：
  1. 搬移后 `C->pidx` 未同步到新 pair ⇒ **游标不变式破了**（实测 `atE_stitchtarget` 8561 次、`atE_endmerge` 53 次 D/seam pair 与 `C->pidx` 不一致）；
  2. 没修源头，改为**消费者侧用第二套定位兜底**——从 `edge->parent/idx` 反查位置重新定位 Cursor（`atE_stitchtarget`/`atE_endmerge`）、用 `C->pidx = C->edge->idx` 就地"修好"、用 leaf 反查重建 `paths[]`（`atE_setpath`/`atE_setcursor`）；
  3. 第二套定位自己又长出配套：沿 `->parent` 链爬树找兄弟 leaf、全树扫描找活 edge、四路邻居搜幸存 edge、一串 `*liveedge*` 小函数；
  4. 结果：函数体 **794 → 1949 行**、文件 **1139 → 2444 行**、删除家族 **194 → 553 行**，而同职责的共同源（linecache `lcD_*`）只有 281 行。
  **教训**：① 现场维护失败只能在**源头**修，"另找一条路把状态问出来"是把 bug 固化进结构，不是修复；② 只要一个字段既能被写、又能被读来定位，它**必然**被当成第二套定位系统——所以读要收口到唯一入口（本项目定为 `atK_fromedge`）、写也要收口到唯一入口（`atN_fixlinks`）；③ 行数达到同源实现 2× 时，**先怀疑有第二套定位 / 兜底路径**，而不是怀疑模型复杂；④ 断言现场不变式（`C->pidx == C->edge->idx`）放在每个搬移出口，让破坏当场爆掉，是防这一类固化的最便宜手段；⑤ **同一根因会分层复现**——修好"身份一致"（`pidx == edge->idx`）后，"位置正确"（Cursor 的 pair 就是承载 `pos` 的 survivor pair）仍可能没维护（实测 `atE_stitchtarget` 处 33653 次同 leaf 异 pair），而旧代码对它的兜底同样是"用回指把 Cursor 搬过去"。**每层都要在 caller 侧出口同步，并各自留断言**（身份 / 位置分别断言），不要以为修了一层就完事。

## 精炼条款

### 一 数据导向：让数据自己说话

- **1.1 先计算，后判断**——把复杂条件中的公共子表达式提到前面，让判断变简短：
  ```c
  // 繁
  if (!ptM_ishole(p, cc-1) && !ptM_ishole(rt, 0) && ...)
  // 简
  hL = ptM_ishole(p, cc-1), hR = ptM_ishole(rt, 0);
  if (!hL && !hR && ...)
  ```
- **1.2 自然数据流代替人工 flag**——计算一个值，让数据本身告诉你答案，而非先设标记后核对。例（`ptD_mergeleaf`）：坏 = 先预制 `merged` 再核对“空间够不够”；好 = `d = pt_min(右大小, 左剩余空间)` 自然区分部分 / 完全合并。`merged` 仍必要（记录“是否合并了整片右叶”，数据流无法直接回答），关键区别：它是**计算的结论**，不是**预设的标记**；flag 只带 1 bit 信息，同类判断各自提前 return。
- **1.3 统一 > 特例**——不为边界情况写单独分支，融进主循环。例（`ptC_freeze`）：坏 = 单独 `if (levels == 0) return;`；好 = 主循环天然处理。同类：不可达的 switch `default:` 消除，越界兜底改主路径后单行 if。
- **1.4 重复分支问“同一数据的不同来源？”**——多个函数共享同一解码逻辑 → 抽参数化 helper，入口各剩 2-4 行。语义有微妙差异时判定等价但保守不合并（合并收益要大于等价论证成本）。

### 二 视觉简洁：简练是减杂质，不是减行

- **2.1 用宏，不用 cast**——`(const char *)p->data` → `ptN_lit(p, cc-1)`；宏不仅短，而且语义自明。
- **2.2 逗号表达式**——同一逻辑单元（同类字段、同一 category）的赋值连成一句：`key->type = TF_TYPE_UNICODE, key->event = TF_EVENT_PRESS;`。多行赋值暗示“独立步骤”，逗号表达“一起发生”，且省行数；散开写仅当赋值之间夹着计算 / 判断。纯赋值的单行 `if` 块用 `,` 取代 `{ }`。
- **2.3 提交语义：`return expr, 状态;`**——把“提交”（状态复位、计数更新）缩到 return 后；动机是视觉语义：一眼看到 return 的意图。块状裸 return 同样收编。**但单 return 优先**：能调整逻辑使函数只有一个 return，比提交语义更强。**适用范围**：不切分自然逻辑中的连贯操作；return 前有两个平行 / 对称操作时，要么全部收进同一个 `return ..., 状态;`，要么全部留在 return 前，禁止只合并其中一个。书写见 `brief_writing.md` §7。
- **2.4 变量少即是多**——删掉只出现一次的栈变量（直接调函数或声明在 for 里）。但**不要重复计算有副作用的表达式**；无副作用且编译器能优化时，重复调用比引入临时变量更清晰。声明尽量内联进表达式（如 `lua_setfield(L, -2, yyjson_get_str(key))`），只留必须的（循环游标 / 输出参数）。
- **2.5 单行形态**——两行块能收成一行时应收成一行；只有多语句才保留 `{}`。书写见 `brief_writing.md` §2。
- **2.6 单行函数与 off 保护**——clang-format 只拆不合，手写单行函数必须保护；off 只允许保护单行函数本体，禁止为覆盖率保护单行 if / 表达式。书写见 `brief_writing.md` §3。
- **2.7 混合初始化声明：非初始化变量在前**——读者必须先扫过非初始化变量（需要留意），初始化变量自解释可略过。`int len, cp = -1, mods = 0;` 正；`int i = 0, cp, r;` 错。
- **2.8 写字符串用带截断 helper**——同函数族的 `writes(buf, len, s)` 与 `snprintf("%s")` 完全等价（拷贝 + 截断 + NUL + 返回字节数），且免 size_t cast。

### 三 循环与迭代：形态即语义

- **3.1 循环递增一律 ++i**——前缀递增是全库铁律。后置 `i++` 仅当递增表达式的值被使用（`out[j++] = c` 是复合语义，可保留）。
- **3.2 循环形态判定**——有 init/cond/inc 完整三要素 → for；纯“跳过到某条件” → while 或 for+continue；终止条件单一且可前置 → `while (cond)` 而非 `for(;;)`（条件在头部是信息密度；`for(;;)` 只留给多体内退出点的循环，且 `if (X) break;` 中 X 明显可前置时必须写 while）；`while (cond) { ...; update; }` 尾有循环变量更新且 update 是纯推进 → `for (; cond; update)`（update 夹业务副作用或体与 update 长依赖时保持 while）；空 for 体用 `continue` 不用 `;`（clang-format 对空 for 体振荡）。
- **3.3 查表循环避免运行时 strlen**——`strlen(tbl[i].name)` 的指针来自运行时索引，编译器无法静态折叠。表字段存 `len`，初始化用 `sizeof(name) - 1`（编译期常量），宏包一层免重复写名字：`#define TFK_MOD(name, mod) {(name), (int)(sizeof(name) - 1), (mod)}`。
- **3.4 顺序字节读取用单一 Cursor 推进**——读多字节序列（utf8 回扫 / 步进）必须一次定位 + Cursor 顺序推进（每次推进更新状态、跨 piece 安全、支持负 delta），禁止每字节 seek / locate 重建 Cursor（铁律：Cursor helper 严禁 locate，见《现场状态纪律》）；utf8 后退：一次定位后回扫 ≤4 字节窗口（负回退 + 顺序读 + 尾部找 lead），窗口 4 字节必含 lead。

### 四 性能与正确性：先于简练

- **4.1 API 形态杜绝 O(n²)**——“看着顺眼”的接口可能是性能陷阱：按索引从 buf 头重扫的参数访问 API，调用方写成 `arg(S,1) + arg(S,2) + ...` 即 O(n²)，且该 API 形态**诱导**调用方写出 O(n²)。判定标准：每次调用是否“从头重扫”？同一数据是否被重复定位？是 → 改成单次扫描 / 迭代器。
- **4.2 迭代器形态三坑**——① 返回字段头指针导致 in/out 参数方向混杂、签名撒谎：用 `int` + `const char **pf` 两 in/out 对称。② 耗尽后置空指针会**重启**（空指针兼首调 / 耗尽双重语义）→ 耗尽置尾哨兵，幂等返回 0。③ 界面臃肿（数组 + struct + dflt 契约）是抽象错误的信号——切回迭代器后整体消失。
- **4.3 数据入口归库自身**——接收调用方指针数组、内部排序后直接存指针 = 指针生命周期依赖调用方（如 `lua_tostring` 指针随 GC 失效，接口层无保证）。判断标准：**被存储的数据必须由库复制进自己的内存，接口只接受值 / 单指针，不接受指针数组**。
- **4.4 迭代算法设计期做均摊分析**——“每个叶容器从 root 重新下降找 hole”实现简单但 O(H·L)。**凡是“循环里重复定位”的设计，写设计文档时就要给均摊论证**；给不出就改为“从当前位置继续”的迭代器。
- **4.5 bug 教训**——① **减法要数清缓冲边界**：当前字节从未进缓冲时只应 `len -= 1`，多减 1 字节；测试注释可能固化错误期望，review 时要追问“为什么少一个字节”，别把测试注释当真相。② **贪婪解析要留退出路径**：允许“到达终止符也算匹配成功”时，终止符会被吃成内容、键名空 → 解析失败；匹配只在分隔符前成立，键名优先。

### 五 命名与分类：名字里藏领域

- **5.1 命名里藏领域**——`ptK_cowedit → ptD_cowpaths`：它是删除流程中的 COW 路径分裂，不是通用工具。函数名反映分类（D=删除, K=光标）而非机制（cow）；简称够用就不需要全称。
- **5.2 工具宏命名与位置**——命名：全大写、不带名字空间字母（`TF_NAMEBUF_SZ` 而非 `tfK_NAMESZ`）。位置：全项目通用的函数式宏集中放 implementation 前部（include 后、NS_BEGIN 前）；数据表宏与常量宏留在绑定位——**只有全项目通用的才挪前部**。表元素计数宏一处定义全库复用，让 `for` 条件保持单行。
- **5.3 绑定层内部函数不带分类码**——分类码（`ptX_name`）只属**库头文件**；绑定层内部工具函数一律 `lpt_` / `ltf_` 前缀（如 `lpt_charstep` 非 `lptM_charstep`）。绑定层无多模块混用，分类码纯噪声。

### 六 与 clang-format 相处

- **6.1 对抗三招**（长条件 / 嵌套三元被拆坏时）——取反 if 条件，让单行短分支在 if 侧而非 else；嵌套三元被拆成错位缩进 → “逐步覆盖”（先赋默认值，再按优先级从低到高覆盖）；多条件 if 超 80 列被拆 → 预计算标志变量，if 恢复单行（Clean C 允许块内连续声明）。
- **6.2 悬挂续行**——逗号表达式 return / 多操作数续行被拆成远列悬空对齐 = 悬挂写法，接受即放弃可读性，也是列宽微调就崩的脆弱形态。修法：改代码而非调格式。书写见 `brief_writing.md` §1。

### 七 注释与重构纪律

- **7.1 函数头注释全删**——函数头注释往往是“做什么”的复述；逻辑不自明应先改实现。输入契约用 assert，输出契约写在函数体内 return 附近，长论证放 design 文档。改代码后必须同步 design 与精炼文档。书写见 `brief_writing.md` §1。
- **7.2 重构前列隐性行为清单**——重构前从被删代码 / 注释提炼行为清单（缺字段默认值、空字段、截断、吞末字段、前导跳过、判定规则），每项映射到既有测试（无测试的补新断言）。隐性契约保障三级：① **消除**（最优先）——让约束成为自然数据流或结构保证；② 使用处 / 实现处注释——约束绑定生效位置；③ 测试兜底——只负责验证，不该是唯一保障。区分“可达分支”与“结构保证分支”：结构不变量可直接去掉检查，不必补测试。流程：先跑基线 → 重构 → 全量测试 + 覆盖率对比（行 100%、分支 ≥95% 不倒退）。
- **7.3 行数预算按伪代码 ×2 估**——伪代码不含 Clean C 声明块、错误传播、assert、断行；**预算失真一倍是常态**：按伪代码 ×2 报，或设计文档直接写 C 骨架。
- **7.4 上升 + 下降合并为单 iter 函数**——树上“找下一个 X”应写成**一个** `pt_next` 式函数（ascend 找可行层 → descend 落点），而非 find/next/descend 三个小函数分散逻辑；首次调用用哨兵初始化统一，消灭 findfirst/findnext 两套入口。
- **7.5 意外修改先评估来源**——diff 与预期不符时：可能是用户改的，也可能是 formatter 或其他进程改的。先正确评估——语义等价性、风格倾向、可能来源——拿不准就停下来询问，**绝不允许对未知修改自作主张保留或回滚**（教训：回滚了一处用户为 clang-analyzer 改的前置 void 写法，白回滚一场）。

### 八 测试与覆盖率

- **8.1 测试期望会固化行为**——测试注释断言“内容应为 X”时，先质疑 X 是否符合协议语义，再信实现；多轮 review + 100% 覆盖率只保证行为稳定，不保证语义正确。
- **8.2 覆盖率缺口先问“能消除吗”，再问“能覆盖吗”**——绝大多数缺口是**可以改写掉的逻辑**，不是不可达代码；豁免清单是最后手段。手段按序：① 行覆盖转分支覆盖（单行 `if (cond) return ...;` 拆两行会出现行缺口 → 错误推送抽 helper 且由可测路径共用；“先计算再判断”）；② 相信 API，删防御检查（宿主语言 / 调用方保证的枚举、越界、非 NULL 契约）；③ 统一 > 特例（条件分支幂等时无条件化）；④ 尾调用消除 else 块；⑤ 死分支删除（恒真条件、不可达 default → 兜底放 switch 后单行 if）；⑥ 三元替代 if/break；⑦ 测试盲区先查参数求值顺序；⑧ gcov 行号映射（条件编译 / 宏展开可能偏移）。豁免清单只留：结构保证、平台分支、依赖外部配置的分支。
- **8.3 X macro 集中错误码定义，且不损行覆盖**——`#define LX_ERRORS(X) X(1, name1) X(2, name2) ...` 一处维护 code+name，switch 内宏展开取名字。**宏展开代码的 gcov 行号映射到宏调用行——执行 switch 即整行覆盖，各 case 无需逐个触发**。配套：不可达 `default:` 消除，越界兜底改为 switch 后单行 if。

### 九 Lua 绑定特例

- **9.1 跨运行时 API 先实测语义差异**——`lua_tointegerx` 在 LuaJIT 与 5.5 语义不一致（前者不检查小数）。绑定内自实现统一版，不依赖平台 API 语义；**凡是跨 5.1 / 5.5 / LuaJIT 的 API，先实测语义差异再直接用**。
- **9.2 lua_next 循环：pop 后栈索引语义变化**——`while (lua_next(L, idx))` 循环内栈为 `[table, key, value]`，pop value 后 key 到栈顶（-1），`-2` 变成外层数据。重构把检查内联进条件时误挪到 pop 之后 → 检查错对象。规则：**栈索引敏感的取值 / 检查必须发生在 pop 之前**；重构后跑全量测试。
- **9.3 错误返回用稳定字符串名**——解码失败返回 `nil, err_name, err_pos`（三值，不堆四值）；err 是**稳定字符串**（非自由文本），`.d.lua` 用 `@alias err_code "..." | "..."` 限死全集——用户可字符串比较，LuaLS 校验拼写。不导出数字常量表（小 API 不配错误表）；错误码字符串用 `lua_pushliteral`。
- **9.4 null 哨兵 = registry 固定表**——JSON null → **registry 里的固定空表**（luaopen 建一次，模块属性暴露），decode 推同表、encode 用 `lua_rawequal` 身份比较识别。对比 lightuserdata：表身份比较**两路都可测**，无“宿主语言无法制造 lightuserdata”的结构分支；**表是宿主语言原生可造的唯一对象 → 哨兵优先选表**。
- **9.5 同类赋值按类型分类抽 builder**——零散的 `key->type = ...` 按类型分类，每个静态类型一个 builder（`tfK_unicode(key, cp)` / `tfK_keysym(key, sym)` / `tfK_function(key, n)`）。**公共字段不入 builder**（来源多变，统一入参反而臃肿）——踩坑：builder 强制默认值会覆盖先行的合法赋值，正解是 builder 只设类型专属字段，公共字段入口统一兜底；动态类型路径不用 builder。太通用的名字是坏味道：一行 helper 若名字比函数体还重，直接内联。
- **9.6 给 helper 加功能的前提是功能能完全融入原流程**——只有当新功能能自然并入 helper 原有的数据流 / 分支 / 循环（不需要额外特例、不需要 `if (...) return another_helper();`）时才加；否则拆分职责或保持原 helper 边界，不要为了“看起来统一”而硬加功能。加功能后若还需调用方补分支 / 补 helper 才能正确，说明该功能一开始就不属于这个 helper。

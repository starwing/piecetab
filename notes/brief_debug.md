# brief_debug.md — 调试工作流（给 Agent 用）

> 教训总结；目标：少走弯路，快速定位根因。C 侧日志用 `test_log`，勿用 lldb。
> 测试命令面见 `notes/brief_tests.md`，库内概念见对应 `notes/design_*.md` / `notes/brief_<lib>.md`。

## 一、铁律

1. **概念不清就问**——无法从代码直接推理的信息不要猜，直接问用户；猜错的成本远大于多问一句。
2. **隔离再定位**——组合操作先拆分（如 splice = remove + append），单独验证每步，确定问题在哪一步引入。
3. **日志佐证一切**——对推理不要自信；关键点插 `test_log` 打印实际值，用日志证据代替猜测。
4. **先跑最小复现**——组合测试先缩小到单个失败参数（如在循环里加 `if (!(pos == 3)) continue;`），快速迭代。

## 二、工作流

- **缩小范围**：`just pt @test_name` 只跑一个测试（`pt` 换成目标库别名）；brute 循环太大就加过滤条件。
- **拆分操作找引入点**：先单独跑组合中的一步，并校验结构不变量，确认问题引入点。
- **复杂算法先与参考实现逐行 diff**：有移植 / 参考关系的代码，参数语义差异常是单字符（如条件写反）；有参考实现就不要从零理解算法。
- **听用户对问题定位的判断**：用户对宏观结构理解更好；用户说“不太可能是 X”，立刻调整方向，不要在 X 上继续深挖。
- **日志分层递进**：函数级（谁调了谁）→ 值级（参数是什么）→ 分支级（进了哪条路径）；一次铺开到**所有可疑区域**，不要“先在 A 打、A 没问题再去 B”。
- **调试结束的汇报**：根因（精确到行）、修复（精确到 diff）、证据（日志 / 测试输出）、影响（全量跑结果：多少 OK、有无新失败）。

## 三、常见弯路与对策

| 弯路 | 表现 | 对策 |
|------|------|------|
| 纠结编译器细节 | 花大量时间分析求值顺序 / UB | 先看代码是否存在概念问题；编译器行为几乎不会是根因 |
| 误读数据结构 | 按自己的理解读字段 / 层级 | 先读设计文档的术语定义，与代码相互验证 |
| 不看文档猜概念 | 对术语有自造理解 | 找对应 design 文档的术语表 |
| 妄想一次修好 | 看到多个错误后一把梭 | 隔离后逐个击破 |
| 不问用户硬猜 | 对着错误输出反复推理但不求证 | 用户知道意图，直接问远比逆推高效 |
| 不听用户方向 | 用户说“不太可能是 X”仍继续修 X | 立刻转向；同一子问题修 3 轮以上先自问方向对不对 |
| 不看参考实现 | 有参考实现却不逐行对比 | 第一步就 diff；单字符 bug 不值得花几轮推理 |
| 手术刀式修复 | 症状在 A 就在 A 处修补 | 先理解数据流本该怎样，再找源头 |
| orig+restore | 操作后用定位 / 重 seek 事后修正状态 | 让数据在操作后自然正确；禁事后补救 |
| 擅自套用参考实现差异 | 参考实现没有某段就删掉 | 领域模型可能迫使差异；不理解的代码不做删除，先问用户 |
| 忽视现场一致性窗口 | 部分现场被修改后仍按全量遍历 | 先确认现场在哪个层级开始不一致，再决定遍历范围 |

## 四、日志与工具

- `test_log(...)` 定义在 `tests/tests.h`（stderr）；结构 / 游标 dump 工具见对应库测试基建（`tests/*_tests.h` 或库 brief）。
- 不要用调试器（lldb）；断言失败 / 崩溃先用日志定位到具体输入，再缩小复现。
- 定位性能瓶颈：在测试循环中按阶段累加 `clock()` 差值、最后一次性打印（`test_log("[prof] A=%lu B=%lu\n", ...)`）；**数据先于优化，别猜瓶颈**。

## 五、Lua 侧调试（editor / 绑定）

- **临时脚本复现**：`/tmp/*.lua` + fake term（`{write/flush/move/size}`），require 模块后直接 `e:render()` + `io.write` 打印——对应 C 侧 `test_log`。
- 渲染断言用屏幕矩阵逐格打印（如 `e.grid:cell(r, c)` → (cp, style)）；先 dump 实际结构再写期望。
- 「单跑脚本对、测试环境错」：先查 `os.exit` 是否在测试文件末尾（run() 收集 `_G`，其后的类永不执行），再查全局状态污染。
- 模块日志开关：如 editor 的 `e.log`（默认写 editor.log）；测试里 `e.log = function() end` 禁用。

## 六、案例教训（压缩版）

- **用户规则是硬约束**：说了“先给根因和方案再改”“禁 orig+restore”，就不得违反；违反的代价是方案被否、信任受损。
- **有参考实现先 diff**：一次单字符参数差异（条件写反）曾让整轮调试跑偏。
- **方向错误要及时止损**：用户多次提示方向后仍在错误子问题深挖，浪费数轮。
- **修症状 ≠ 修根因**：异常状态（越界索引、零计数）出现时，追问“它是怎么产生的”，而非在异常状态下加特判。
- **日志层级要对**：一次铺开所有可疑函数，而不是逐层深入。
- **不理解的差异不要删代码**：参考实现里没有的调用可能是领域必需；遇到不一致先问用户。
- **API 坏味道会被性能问题暴露**：返回值职责重叠、next/prev 语义不对称会迫使调用方写笨拙代码；性能笨拙先想 API 形态。
- **性能数据先于优化**：用户直觉“校验慢”由 `clock()` 证实；瓶颈常不在直觉处。
- **两条路径的收尾逻辑必须对齐**：同一操作的多条实现路径（如不同删除入口）状态收尾不一致，会让 bug 潜伏到后续才炸。
- **状态正确 ≠ 索引有效**：偏移量正确不代表路径 / 索引有效，逐层检查。
